# Фаза 5 — Полировка и деплой

Мини-спека к `context/project-overview.md` (Дорожная карта, Фаза 5). Цель фазы — убрать блокировку навигации при загрузке анализа, довести статус обработки до пользователя в реальном времени и добавить лёгкую геймификацию (streak + бейджи) поверх уже накопленных данных трекинга.

## Решения

- **Фоновая обработка PDF** — `uploadLabReport` больше не ждёт Gemini внутри Server Action (источник блокировки навигации — тот же класс проблемы, что решали в Фазе 4 для чата через Route Handler). Action быстро создаёт `LabReport(status="processing")` и возвращается, парсинг вынесен в `after()` из `next/server`.
- **Realtime — пересмотрено в процессе реализации.** Изначальный план (клиент подписывается на Supabase Realtime напрямую через anon key) оказался несовместим с RLS, который включили перед этой фазой: Realtime фильтрует события тем же RLS, а RLS — deny-all, потому что авторизация — Auth.js, не Supabase Auth (нет `auth.uid()`, на который могла бы опираться политика). Открывать anon key под политику «отдавай строки с этим `userId`» означало бы повторно открыть дырку, которую только что закрыли. Решение: `GET /api/labs/[id]/status` — SSE-эндпоинт; сервер сам подписывается на Supabase Realtime через `service_role` (обходит RLS безопасно, ключ не уходит в браузер) и транслирует в браузер только уже авторизованный статус одного отчёта. Клиентский `LabStatusWatcher` слушает SSE и вызывает `router.refresh()` при `done`/`error`. `LabReport` добавлена в публикацию `supabase_realtime`.
- **Геймификация — через отдельную таблицу, не на лету.** Проект многопользовательский, и момент получения бейджа — значимое событие (нужно уведомление, правило подсчёта не должно задним числом терять уже заработанные бейджи при изменении логики) — это случай, где write-on-earn правильнее пересчёта при каждом открытии дашборда. Каталог бейджей — константа в коде (`src/lib/badges.ts`), не отдельная таблица: правила подсчёта — код, не данные. Текущий streak не хранится — живое расчётное поле, может уменьшаться при пропуске дня; в `Achievement` попадает только разовое событие «порог достигнут».
- **Логотип / loading-анимация** — реализована как часть статуса обработки (ровно то место использования, которое и имелось в виду при согласовании логотипа): столбики «дышат» высотой (не scale), с несимметричным easing, учитывает `prefers-reduced-motion`.
- Email-напоминания сознательно вынесены из этой фазы — отдельной Фазой 6 в `context/project-overview.md`.

## Модель данных (добавлено к `prisma/schema.prisma`)

- `Achievement`: `id`, `userId` (FK → User, `onDelete: Cascade`), `badgeKey`, `earnedAt` — `@@unique([userId, badgeKey])`

## Экраны

1. `/labs` — список отчётов: во время `processing` строка показывает анимированную иконку (`RisingBarsLoading`) вместо точки-индикатора и сама обновляется на `done`/`error` без перезагрузки страницы
2. `/dashboard` — секция «Достижения»: текущий streak + сетка из всех бейджей каталога (полученные — с датой, остальные — полупрозрачные, с описанием условия)

## Что делает агент (в коде)

1. Включить Realtime replication для `LabReport` (`ALTER PUBLICATION supabase_realtime ADD TABLE "LabReport"`)
2. Переписать `uploadLabReport`: создание записи + загрузка файла — синхронно; парсинг через Gemini — в `after()`
3. `GET /api/labs/[id]/status` (SSE, подписка на Realtime через `service_role`, проверка владения отчётом перед подпиской) + клиентский `LabStatusWatcher`
4. Модель `Achievement`, каталог бейджей и `checkAndAwardAchievements(userId)` в `src/lib/badges.ts`; вызов из записи `HabitLog`/`MealLog`, из `after()` при переходе `LabReport` в `done`, из первого сообщения пользователя в чате
5. Карточка «Достижения» на дашборде
6. `RisingBarsLoading` — анимация подключена в `StatusPill` для статуса `processing`
7. Обработка ошибок по NFR: сбой в `after()` пишет `status="error"` + `errorMessage`, долетает через тот же SSE-канал, что и `done`

## Что делает пользователь (вне кода, руками)

1. Прогнать сценарий: загрузить PDF → статус меняется в реальном времени без обновления страницы, с анимацией во время обработки → навигация по сайту не блокируется во время обработки → увидеть новый бейдж/серию на дашборде
2. Проверить деплой на Vercel

## Критерии приёмки

- [x] Загрузка PDF не блокирует навигацию по сайту, пока анализ обрабатывается в фоне
- [x] Статус обработки анализа (`processing` → `done`/`error`) обновляется в интерфейсе `/labs` в реальном времени, без ручного обновления страницы
- [x] Дашборд показывает текущую серию дней трекинга (streak) и полученные бейджи-достижения
- [x] Ошибка фоновой обработки долетает до пользователя через realtime, не зависает в статусе `processing` навсегда
- [x] `npm run build` без ошибок
- [ ] Изменения задеплоены на Vercel и проверены на проде

Первые пять пунктов проверены сквозным сценарием самим пользователем локально (2026-10-09): вход, загрузка PDF, SSE-соединение держалось всё время фоновой обработки (~44с) и само вызвало обновление страницы без участия пользователя, оба ожидаемых бейджа (`FIRST_LAB_REPORT`, `FIRST_CHAT_MESSAGE`) подтверждены записью в БД.
