# Фаза 5 — Полировка и деплой

## Цели

- [ ] Загрузка PDF не блокирует навигацию по сайту, пока анализ обрабатывается в фоне
- [ ] Статус обработки анализа (`processing` → `done`/`error`) обновляется в интерфейсе `/labs` в реальном времени, без ручного обновления страницы
- [ ] Дашборд показывает текущую серию дней трекинга (streak) и полученные бейджи-достижения
- [ ] Ошибка фоновой обработки (LLM/Storage недоступны и т.п.) долетает до пользователя через realtime, не зависает в статусе `processing` навсегда
- [ ] `npm run build` без ошибок
- [ ] Изменения задеплоены на Vercel и проверены на проде

## Заметки

### Решения

- **Фоновая обработка PDF** — сейчас `uploadLabReport` в [actions.ts](../src/app/(protected)/labs/actions.ts) синхронно ждёт ответ Gemini внутри Server Action — это и есть источник блокировки навигации (тот же класс проблемы, что решали в Фазе 4 для чата через Route Handler, см. `context/architecture.md` → «Server Actions vs Route Handlers»). Предлагаемое решение: Server Action быстро создаёт `LabReport(status="processing")` и возвращается сразу, а сам парсинг PDF выносится в `after()` из `next/server` (официальный механизм Next.js для работы после отправки ответа, корректно работает на Vercel через `waitUntil`) — без отдельного Route Handler и без «стрельни и забудь» fetch, который на serverless ненадёжен.
- **Realtime** — Supabase Realtime (подписка на Postgres-изменения строки `LabReport` через `@supabase/supabase-js`), а не SSE: провайдер уже в стеке, не нужен отдельный стриминг-эндпоинт, клиент сам переподключается. SSE остаётся только там, где уже есть (стриминг токенов чата — другая по природе задача).
- **Геймификация — через отдельную таблицу, не на лету.** Проект многопользовательский (см. `context/project-overview.md`), и «момент получения бейджа» — значимое событие (нужно показать уведомление, и правило подсчёта не должно задним числом терять уже заработанные бейджи при изменении логики) — это ровно тот случай, где write-on-earn правильнее пересчёта при каждом открытии дашборда. Дизайн:
  - Новая модель `Achievement`: `id`, `userId` (FK → User, `onDelete: Cascade`), `badgeKey` (строка-ключ бейджа), `earnedAt`. Уникальный индекс `@@unique([userId, badgeKey])` — защищает от дублей при повторном срабатывании проверки.
  - Каталог бейджей — константа в коде (`src/lib/badges.ts`), не отдельная таблица: `{ key, title, description, check(stats) }` на каждый бейдж. Правила подсчёта — код, не данные, менять их всё равно нужно через деплой, отдельная таблица-каталог здесь не добавляет пользы.
  - Один общий `checkAndAwardAchievements(userId)` в `src/lib/badges.ts`: считает текущую статистику (streak, число отчётов/сообщений/дней трекинга), прогоняет через каталог, вставляет только новые `Achievement` (которых ещё нет для этого `userId`+`badgeKey`). Вызывается после: записи `HabitLog`/`MealLog`, перехода `LabReport` в `done` (внутри `after()`), первого сообщения пользователя в чате.
  - Текущий streak (число дней подряд) **не** хранится — это живое, дневное число, может уменьшаться при пропуске дня, остаётся расчётным полем для дашборда. В `Achievement` попадает только разовое событие «серия достигла N» как отдельный бейдж.
  - Черновой набор бейджей и пороги (нужно подтверждение/правки): «7 дней подряд» (streak ≥ 7), «Первый анализ загружен» (`LabReport.status="done"` ≥ 1), «30 дней трекинга» (дней с активностью, не обязательно подряд, ≥ 30), «Первый вопрос в чате» (`ChatMessage.role="user"` ≥ 1).
- **Логотип / loading-анимация** — открытый вопрос из `context/project-overview.md` («дыхание» столбиков Rising Bars) — статус обработки PDF в реальном времени является ровно тем местом использования, которое ждали. Кандидат на реализацию в этой фазе, но требует отдельного прохода по деталям анимации (скорость, easing, анимация высоты) — не блокирует остальной объём фазы.

Email-напоминания вынесены из этой фазы — отдельной Фазой 6 в `context/project-overview.md`.

### Модель данных (добавляется к `prisma/schema.prisma`)

- `Achievement`: `id`, `userId`, `badgeKey`, `earnedAt` — 1:N от User, `@@unique([userId, badgeKey])`

### Что делает агент (черновик, до согласования)

1. Включить/проверить Realtime replication для таблицы `LabReport` в Supabase
2. Переписать `uploadLabReport`: создание записи + загрузка файла — синхронно и быстро; парсинг через Gemini — в `after()`
3. Клиентский компонент статуса на `/labs`: подписка на `postgres_changes` по `id` текущего `LabReport`, обновление UI без reload
4. Добавить модель `Achievement` (`prisma db push`), каталог бейджей и `checkAndAwardAchievements(userId)` в `src/lib/badges.ts`, вызвать из записи `HabitLog`/`MealLog`, из `after()` при `LabReport.status="done"`, из первого сообщения в чате
5. Карточка «Достижения» на дашборде: живой streak (расчётный) + список полученных `Achievement`
6. Обработка ошибок по NFR: сбой в `after()` обязан записать `status="error"` + `errorMessage`, и это обновление должно долететь через realtime так же, как `done`
7. Финальный QA-проход перед деплоем, обновление документации

### Что делает пользователь

1. Включить Realtime replication для `LabReport` в Supabase (Database → Replication)
2. Прогнать сценарий: загрузить PDF → статус меняется в реальном времени без обновления страницы → убедиться, что навигация по сайту не блокируется во время обработки → увидеть новый бейдж/серию на дашборде
3. Финально проверить деплой на Vercel
