# Правила взаимодействия с AI при разработке

## Общие принципы

- Реализуется только то, что описано в активной мини-спеке (`context/current-feature.md` / `context/feature/phase-N-*.md`).
- Значимые архитектурные решения — перед внесением изменений согласовываются с пользователем и фиксируются в разделе «Решения» мини-спеки (пример — `context/feature/phase-4-rag-chat.md`).
- Тестовые данные, заведённые для проверки фичи, удаляются из БД/Storage после проверки, а не коммитятся.
- Пользователь не является разработчиком с опытом в вебе — код и новые концепции (роуты, хуки, RAG и т.п.) объясняются подробно, по запросу, с разбивкой по слоям и примерами кода из реального проекта, а не абстрактно.

## Рабочий процесс (по фазам дорожной карты)

Проект развивается фазами из `context/project-overview.md`. Для каждой новой фазы — через навык `feature` (`.claude/skills/feature/`, действия `load`/`start`/`review`/`complete`, см. `SKILL.md` там же):

1. Написать мини-спеку в `context/current-feature.md` (разделы «Решения», «Модель данных», «Экраны», «Что делает агент», «Что делает пользователь», «Критерии приёмки» — см. готовые примеры в `context/feature/phase-*.md`) — либо вручную, либо действием `feature load`
2. `feature start` — создать ветку `feature/<slug>` от `master` и начать реализацию
3. Реализовать функциональность
4. Проверить сквозной сценарий локально (`npm run build` без ошибок + ручная проверка критериев приёмки) — можно действием `feature review`
5. Закоммитить в ветку фичи (см. «Git» ниже)
6. `feature complete` — зафиксировать архив мини-спеки, обновить `current-feature.md`, запушить ветку и открыть PR в `master`
7. Смёржить PR (вручную через GitHub или по явному запросу), затем задеплоить/подтвердить на проде
8. Удалить ветку фичи после мёржа

## Git

Каждая фаза/фича/фикс — в своей ветке от `master`:

```text
feature/<slug>   — новая фаза или фича
fix/<slug>       — багфикс
chore/<slug>     — служебная задача (докс, конфиг)
```

Публикация — через GitHub Pull Request в `master`, не прямой мёрдж (даже соло-разработка: PR-история — часть портфолио). Коммит только после того, как функциональность проверена и `npm run build` проходит; сообщение — короткое summary в духе существующей истории (`git log`), например `Phase 4: RAG chat, recommendations, knowledge base`.

Пуш ветки и создание PR — действия, видимые вовне и не тривиально отменяемые: по умолчанию каждый раз подтверждаются у пользователя перед выполнением, даже внутри действия `feature complete`. Мёрдж самого PR в `master` тоже подтверждается отдельно (или выполняется пользователем через GitHub). Ветка фичи удаляется только после подтверждённого мёржа PR.

## Если возникла проблема

Если решение не найдено после 2–3 попыток — остановиться и объяснить проблему, а не пытаться дальше вслепую.

## Внесение изменений в код

- вносить минимально необходимый объём изменений под активную задачу;
- не менять сторонние модули без необходимости;
- не добавлять дополнительный функционал, если он не согласован;
- придерживаться существующих паттернов, стиля и архитектуры проекта (см. `context/architecture.md`).

## Проверка качества

При ревью кода обращать внимание на:

- Безопасность (авторизация, доступ к данным, валидация — особенно в route handlers и server actions)
- Производительность (запросы к БД, лишние рендеры UI, кеширование)
- Корректность логики (граничные случаи, обработка ошибок, поведение при некорректных данных)
- Согласованность (единый стиль реализации, отсутствие лишних усложнений)
- Соответствие NFR по обработке ошибок из `context/architecture.md` (ожидаемые ошибки — try/catch на месте, непредвиденные — error boundary)
